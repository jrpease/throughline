# Does the variant-axis convention hold? — measurement

**Date:** 2026-08-31
**Gate for:** #39's Decision 2 — whether `unknown-variant-value` is worth
building, or whether the narrowing it required leaves it catching nothing.
**Verdict:** it holds **exactly** where ThroughLine generated both sides, and
degrades where a human wrote the record. The rule stays in v1. One spec-breaking
bug was found that no amount of reading would have surfaced.

## Why this run exists

The spec's Decision 2 rests on a convention nothing enforces: that a doc
record's variant **axis name** is the code component's **prop name**. Two
readings of the repo's own documents predicted it would fail:

- the schema's example record names the axis `type`
  (`references/component-doc-schema.md:30-33`);
- `skills/storybook-chromatic-builder/SKILL.md:80` phrases the convention as
  "type/size/state".

React components conventionally take `variant`. Both the spec's first draft and
its critic review concluded from this that #39's headline case —
`variant="tertiary"` — would fall to an advisory and the gate would exit 0.

**Neither had looked at a real record.** This run does.

## Sources

Every repo on this machine holding throughline doc records:

| repo | records | kind |
|---|---|---|
| `throughline-sample` | 14 | generated by ThroughLine end to end |
| `zygarden-frontend` | 1 | real app, record hand-authored for an existing component |

Read-only. Neither repo was modified.

## Finding 1 — in a generated system the convention holds exactly

Declared axis names and values, against each component's own `cva` definition:

| record | declared values | code |
|---|---|---|
| `Button.variant` | default, secondary, destructive, outline, ghost, link | **identical** |
| `Badge.variant` | default, secondary, destructive, outline | **identical** |
| `Card.variant` | default, elevated | **identical** |
| `Button.size` / `Input.size` / `Avatar.size` | sm, md, lg | **identical** |

**Zero mismatches across 14 components** — names *and* values. The record and
the component are derived from the same Figma variant matrix, so they agree by
construction rather than by anyone remembering to keep them in step.

The schema's `type` example is an example. It is not what the generator emits,
and reasoning from it was the error both earlier analyses made.

## Finding 2 — a hand-authored record breaks it, and the prose admits it

`zygarden-frontend`'s only record, `SurfaceCard`, declares an axis `state` with
values `static` / `collapsed`. Its own prose reads:

> "Code: accordion=false (expanded is ignored)."

That axis is not a prop. It names a **conceptual state that maps to a
combination of two props**, and the mapping exists only in English. No gate can
check it, and none should try — the rule simply never fires there, which is safe.

The shape of the result is the useful part: **the convention holds where
ThroughLine generated both sides and degrades where a human wrote a record for a
component they did not generate.** That is also where drift is most likely, so
the rule is weakest exactly where it would be most useful. Recorded in the spec's
risks rather than smoothed over.

## Finding 3 — the bug reading would not have found

`design-system.json`'s `components.built` holds **display names**:

```json
["Button", "Spinner", … , "Select Menu", "Select Menu Item"]
```

The code exports and uses `<SelectMenu>`. The spec's `unknown-component` rule
matches JSX element names against `components.built`, so as written it reports
`<SelectMenu>` as an unknown component — **a hard failure on entirely correct
code, in the only sample system that exists.**

That is precisely the "fastest route to the gate being switched off" scenario
the spec names as its existential risk, live on day one.

Fix is cheap and already in the repo: `normalizeKey` in
`validate-token-output.mjs` (lowercase, strip non-alphanumerics) exists for this
exact class of problem. Both sides go through it. Nothing in the schema claims
`name` is a code identifier, and nothing should be changed to make it one — a
display name is right for a doc surface. The gate normalises.

## Finding 4 — half of all attributes are invisible to regex extraction

Scanning the sample app and package sources for JSX attributes on known
components:

```
attributes on known components : 33
  matched a declared axis/state: 2
  unmodelled                   : 15
  dynamic (not a literal)      : 16
```

**16 of 33 — 48% — are expressions (`variant={x}`), not literals.** The spec
already reports those as `dynamic-value` advisories, but a per-item advisory
list does not convey a proportion. The figure moves to the report headline.

The low match count is **not** a convention failure, and reading it as one would
be the third wrong conclusion in this document's history. The unmatched literals
were `label` (8), `value` (6) and `initials` (1) — content props, which no
variant axis should ever have covered. The spec already classifies them
correctly as advisories.

## What changed in the spec

1. `unknown-component` normalises both sides before matching. **Required** —
   without it the gate fails correct code today.
2. Decision 2 keeps the variant rule, justified by Finding 1 rather than by
   argument, with the coverage floor re-justified: it detects *which kind of
   system* the gate is pointed at, at run time, instead of assuming.
3. The dynamic-attribute proportion moves into the report headline.
4. Finding 2 is recorded as a stated risk: the rule is weakest in retrofitted
   systems, which is the wrong way round.
5. Phase 4 — a real props block in the doc record — stays deferred. Finding 1
   says it is not the blocker the first draft assumed.

## What this run does not establish

- **One generated repo and one hand-authored record.** The generated case is
  strong evidence about the generator, which is deterministic; the hand-authored
  case is a single counter-example, not a rate.
- **No drift was present to catch.** Both repos are internally consistent — the
  run measured whether the rule *could* fire, not whether it catches real drift.
  That is what the phase 2 end-to-end run against a drifted app is for.
- **Nothing about the colour rule**, which was not exercised here.
