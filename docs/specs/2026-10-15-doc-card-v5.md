# Doc card v5: the documentation pilot layout

Status: spec
Reviewed: 2026-10-26 — ready to plan (fourth pass asked for two sentence fixes, since applied)
Date: 2026-10-15

## Goal

ThroughLine's Figma doc card today is a component set with a hand-made header and
one scripted band (Usage, `scripts/lib/doc-card-render.figma.js`, renderer `'4'`).
Manyfest's "Documentation Pilot" artboard (file `0AgaYH2xuGNKKDW1pRYLkg`, page
"🗄️ Documentation template", artboard `23546:2623`) shows a better shape: a dark
header, then stacked white bands for specimen, variants, properties, usage,
accessibility and tokens, with live instances and token swatches in them.

After this ships, every documented component gets a card in that shape, rendered
from its record plus what Figma already knows (its properties, variants and
variables). The card works for any design system and uses no particular brand.
The chrome (header, band titles, chips) comes from two kit components the
designer can restyle.

## Non-goals

- Anatomy, Content, Platform differences, Related, and live Do/Don't examples.
  Each becomes its own issue (decision 22).
- A separate docs page. Cards stay where they are (decision 6).
- A separate light/dark kit preview (decision 13).
- Figma slots. No band uses one (decision 14).
- Copying Manyfest's brand, fonts, colours or `_Doc/Band` slot structure.
- Changing the record schema. The record stays prose and the structural facts are
  read from Figma (decision 3).

## Decisions

| # | Decision | Chose | Why | Rules out |
|---|---|---|---|---|
| 1 | Who draws the chrome | Hybrid. Kit components in Figma for the header, band titles, ledes and chips; the renderer draws each band's content (tables, example rows) in tested code | Designers restyle the chrome in Figma; content layout stays testable | Everything drawn in code; everything a hand-made template |
| 2 | Which bands ship | The "ready now" set: Header, Specimen (the live set, untouched), Variants & meanings and States (both with live instances), Properties (from Figma), Usage (text lists plus Do/Don't as text), Accessibility, Tokens used (swatches). Later, each as its own step, cheapest record additions first: live Do/Don't examples and Related, then Content, then Platform differences, then Anatomy last | Ships what the record and Figma already support; holds back anything that needs new record fields | Doing the whole pilot in one release; Anatomy before the rest |
| 3 | Where structural facts come from | Properties, variant axes and token values are read live from Figma at render time. The record stays canonical for prose | Figma already has them, and copying them into the record would add a second source that can drift | Adding properties or token values to the record |
| 4 | Brand | None. Bind to the project's own semantic variables and text styles, recorded like `docCardVariables`. A missing name stops the run and names it; nothing has a hard-coded fallback. When the `surfaceHeader` role is picked (decision 20), the suggestion is an inverse surface if the project has one, otherwise the plain surface. The renderer only ever reads the recorded name | Must work on any design system | Manyfest's look; hard-coded hex or font fallbacks |
| 5 | How the kit is found | The renderer draws the kit inside the first render that needs it, on a `Documentation Kit` page. Each kit component is tagged with shared plugin data (`throughline` / `docKit` = `header` or `bandHeader`) and found by that tag after that. `figma.docKit` in `design-system.json` records the Figma file key the kit was drawn in (`{ fileKey }`); it holds no node ids. The plugin can't read the open file's key (`figma.fileKey` is private-plugin only, `docs/specs/2026-10-13-figma-adherence-gate.md:155`), so the first drawing also tags `figma.root` with shared plugin data `throughline` / `docKitFile` = the manifest's `figma.fileKey`, passed in by `doc-card-payload.mjs`. On later renders a root tag that is missing or differs from `figma.docKit.fileKey` is the wrong-file case: it stops the run and names both keys; the same file with no tagged kit stops the run rather than drawing a second kit. To get a kit back after deleting it, set `figma.docKit` to `null`; the next render draws a fresh one. The first drawing binds every fill to recorded roles: the header's `Status` chips use `tonePositive` (stable), `toneCaution` (draft, beta) and `toneNegative` (deprecated; chosen 2026-10-26 over a text role or a new neutral role). The kit components' property names (title, summary, date and `Status` on the header; title, lede and the Unreviewed toggle on the band header) are fixed in the Plan; decision 21 and audit item 4 enforce whatever names it records | Survives renames and moves; a deleted kit is reported, not silently redrawn | Finding the kit by node name |
| 6 | Where cards live | They stay where they are, wrapped around the live component set, and become the full artboard | The set doesn't move, so instances stay attached | A separate docs page; moving sets |
| 7 | How a card is addressed | The card frame gets shared plugin data `throughline` / `docCard` = the component name. `doc-card-payload.mjs` takes a component name, not a node id. The render searches every page of the file (`findAllWithCriteria` on the shared plugin data) for that tag. Two cards with the same tag stop the run and name both. component-builder tags a new card when it creates the card frame, so a card built after v5 ships is never untagged. An untagged card (every v4 card) needs an optional `--node-id <id>` on its first v5 render: the renderer checks that the node holds a component set with that name, then tags it. No tag and no `--node-id` stops the run, names the component and asks for the card's node id. The search loads every page first (`figma.loadAllPagesAsync()`) | Node ids aren't stored anywhere today and go stale | Passing node ids around |
| 8 | What the variant and state examples are | Instances of the default variant with one axis changed. A missing combination is noted in its row and in the run summary | Shows each option on its own, without a full matrix | Dropping the whole matrix in; silently skipping a missing combination |
| 9 | How tokens are shown | Colour tokens get a swatch bound to the variable. Other tokens show their name and resolved value. An effect style shows a preview tile bound to the style (decision 26). A name that doesn't resolve is listed as missing | The swatch stays live when the variable changes | Static hex swatches; leaving missing tokens out without a word |
| 10 | What the Properties band shows | Every `componentPropertyDefinitions` entry, including variant axes with their options, with its type and default | It's the full contract a designer works against | Only the variant axes |
| 11 | How provenance shows | A band whose blocks are all unprotected under the schema's tiers (`references/component-doc-schema.md:69-81`: no block's provenance includes `user` or `imported`, and a block with no provenance counts as unprotected) gets a chip labelled **"Unreviewed"**, filled with the `toneCaution` role. The rule applies to any band holding at least one record block, judged on those blocks alone: Usage, Accessibility, and the meanings in Variants & meanings, States and Tokens used. Properties (all from Figma) never gets the chip; Specimen never does either | The user rejected "Draft" ("doesn't quite feel right"); "Unreviewed" says what's actually missing | A "Draft" label; a provenance chip in the header (see 15) |
| 12 | Empty bands | Not rendered. Specimen always is | No empty sections | Placeholder bands |
| 13 | Light and dark | One kit that follows the variable mode | Modes already handle it | A second kit; a preview of both modes |
| 14 | How the template is built | Only `_Doc/Header` (the whole header) and `_Doc/Band header` (title, lede, Unreviewed chip) are kit components. Each band is a frame the renderer makes, holding a `_Doc/Band header` instance and the content. Its surface, radius and padding are bound to recorded variables. Specimen is the same frame with the live set inside | A main component can't sit inside an instance, so the Specimen band can't use a slot. One band shape for every band, and no first-ever slot to build | Manyfest's `_Doc/Band` with a slot; giving Specimen a different band shape |
| 15 | Who owns the status chip | One chip in the header: the existing status, now a `Status` **variant property** on `_Doc/Header` with options `draft` / `beta` / `stable` / `deprecated`. Designers style each option's chip in the kit. Finalize sets the variant on the header instance; it no longer rebinds a fill. The renderer writes title, summary and date, and never the status, with one exception: the v4 → v5 migration (decision 19) reads the component's status from the manifest (`components.meta[name].status`, which finalize writes before it touches Figma) once and sets the variant to match, ignoring case. It never reads the old chip, which can be the one stale copy when finalize skipped a card. A value that isn't one of the four options (e.g. `final`) stops that card's migration and names the card and the value (chosen 2026-10-26). The Unreviewed chip is on bands only | One owner per field; no repeated chip. The manifest is the status finalize writes first. A text property can't change the chip's colour, and an instance fill override breaks when a designer restyles the chip (chosen 2026-10-26) | A Draft chip in the header; the renderer writing the status on a normal render; finalize rebinding fills inside the instance |
| 16 | Width | 1440 (today's floor of 3 columns at the widest 480 column unit, carried over) or the specimen's width plus padding, whichever is bigger. The specimen's width is read from the set alone, never from the card or a band, and the specimen never fills the card's width; otherwise each render widens what the next one measures (`scripts/lib/doc-card-plan.mjs:20-24`). Every other band fills the width. The column grid goes, and each band lays out its own table or two columns | Wide sets (Button has 108 variants) have to fit | The 480-wide column grid; a fixed 1440 |
| 17 | Band order | Header (summary) · Specimen · Usage (description as its lede, then when to use / use something else, then Do and Don't in two columns, each with a rule bound to `tonePositive` or `toneNegative`; until Steps 2–3 ship, also a plain-text block of variant meanings, state meanings and accessibility, per decision 22) · Variants & meanings · States · Properties · Accessibility · Tokens used | Usage is the text people read first; the reference tables go lower | The pilot's order, with Usage lower down |
| 18 | What the hash proves | Two hashes, both stored in the manifest at `components.meta[name].doc.surfaces.docCard` beside `src` and `renderer`. `recordHash` (new) covers the part of the layout that comes from the record: Node predicts it and a mismatch fails the run, as today. `render` covers the whole layout, including what was read from Figma; nothing predicts it. `docs:check` is unchanged for the card: it reads `src` (stale) and `renderer` (upgrade available) but never `render`, because it can't read Figma and reports the card's edits as unverified (`scripts/docs-check.mjs:57-73`). `render` is kept as the stamp of the last full draw, for a later live re-read of the card to compare against. The summary returns the rows read from Figma so they can be checked by eye | Node can't see the Figma reads, but it can still prove the record arrived intact | Dropping the prediction; pretending Node can predict the whole render |
| 19 | Migration | Renderer v5. Existing cards report `layout-upgrade-available` and upgrade on their next render: the old header frame becomes a `_Doc/Header` instance, the existing set is wrapped in a Specimen band without leaving the card, the old `Usage` band is deleted, and the new bands are added. The manifest status sets the header's `Status` variant (decision 15). A card holding more than one component set still refuses, as v4 does (`scripts/lib/doc-card-render.figma.js:51-60`): it has to be split into one card per component first | Instances stay attached; same upgrade path as v4. One component per card keeps the tag, the hash and the bands simple (chosen 2026-10-26) | Rebuilding cards from scratch; a one-off migration script; cards holding several sets |
| 20 | New variables and text styles | `figma.docCardVariables` gains `surfaceBand`, `surfaceHeader`, `textOnHeader`, `radiusBand`, `toneCaution` (the Unreviewed chip's fill, decision 11, and the draft and beta status chips' first fill, decision 5). A new `figma.docCardTextStyles` has `title`, `bandTitle`, `body`, `caption`. Both are picked once, written back, and read on every render. Projects that already have the nine fill in only the new ones. `Body/Default` stops being hard-coded and becomes the suggested `body`. Manifest schema 7 → 8 adds `docKit` and `docCardTextStyles`, both defaulting to null, and `surfaces.docCard.recordHash` (decision 18), absent until the first v5 render. A missing name stops the run | Same pattern as the nine roles; nothing guesses between renders | Hard-coded style names; a separate config file |
| 21 | Once the kit exists | Designers own it. The renderer never redraws an existing kit component; it only sets that component's properties by name. A deleted or renamed property stops the run and names it | A designer's restyle must survive the next render | The renderer quietly rebuilding or "repairing" the kit |
| 22 | Release steps | Step 1: schema 8, kit, header, Specimen band, tagging and lookup by name, v4 migration, Usage band (carrying v4's variant meanings, state meanings and accessibility as plain text, so no release drops content; chosen 2026-10-26). Steps 2 and 3 move that text into their bands. Step 2: Variants & meanings and States with live instances, plus Properties. Step 3: Accessibility and Tokens used. Each step is a v5.x with its own live run on the sample. The later bands (decision 2) each get a GitHub issue once this spec lands | After Step 1 the card already looks like the pilot; later steps add bands without changing the frame | One big release |
| 23 | Testing | The planner stays pure. The values the renderer reads from Figma (properties, available variants, token values) are passed in as plain data, so Node tests cover every band, including missing combinations, missing tokens and skipped empty bands. Live proof for each step: every sample card re-rendered on `OCiZiGpsJ4ncPD8r205BjC` (13 cards today; Step 1 first splits `Select Menu — Documentation`, decision 19, making 14, and changes the three sample components whose manifest status is `final` (Tooltip, Select Menu, Select Menu Item) to `stable` in the manifest, decision 15; their records already say `stable`, and leaving them alone avoids a re-projection) with the record hash matching Node's; one run on a second file; and a fresh agent running `/document-component` from the command file alone | The renderer only runs in Figma, so the logic has to live where Node can test it | Renderer logic that can't be tested; live proof on the sample only |
| 24 | Other callers | component-builder Step 4.5 and component-pipeline stage 3 change no rendering logic: they pass the component name instead of a node id and pick up v5 automatically; component-builder also tags the card frame it creates (decision 7). Finalize changes: `doc-card-payload.mjs` gains a status mode (`--status <value>`) that finds the card by its tag and sets the header's `Status` variant, replacing finalize's own chip-locating script (`references/figma-component-standards.md:368-391`, `skills/storybook-chromatic-builder/SKILL.md:374-382`); finalize then re-renders as today. Audit items change: 3 (the column-unit exception goes; band chrome must bind), 4 (the deterministic names become the kit's property names), 7 (the header division is the `_Doc/Header` instance), and 11 (checks the card's tag, that the kit is recorded, the `recordHash` match, and that no band uses a raw value) | Renders already go through `doc-card-payload.mjs`; giving finalize's status write the same entry point means one way to find a card | Each caller rendering its own card; finalize keeping a separate card lookup |
| 25 | How the Variants and States bands match record axes to Figma axes | The drift comparer's rules (`compareComponents`, `scripts/drift-check.mjs:111-160`), moved into a shared helper both use: names match with `composeFold` (case and punctuation ignored); a Figma axis folding to `state` pairs with `record.states`; failing a name match, a whole record axis pairs with a whole Figma axis of the same options, as renamed. An unmatched axis or option still gets its meaning row, with no instance, and a note in the row and the run summary (as decision 8) | One rule for both commands; case and punctuation differences (`State` / `state`, `Top` / `top`) keep their examples (chosen 2026-10-26). The sample's two renames (Radio, Tooltip) were reconciled on 2026-10-15 (`docs/notes/2026-10-15-drift-reconcile-live-run.md`), so the rename path has no live case there; Node tests cover it | Exact names only; a second matcher |
| 26 | Where the Tokens used list comes from | The record's `tokensUsed`, each name resolved to a Figma variable for its swatch or value (decision 9). Each name is matched as-is after `.` becomes `/` (the sample's records already use slashed names). A name that matches no variable is then looked up as an effect style (e.g. `Focus Ring`, `Elevation`), shown with its name and a preview tile bound to the style (chosen 2026-10-26). A name matching neither is listed as missing. This assumes the project's variable and style names are the record's names. A system whose variables carry a prefix the record doesn't (unlike `scripts/verify-check.mjs:75-95`, which matches on the tail of the path) shows every token as missing; the live runs record how many resolve on the sample and on the second file | The record says which tokens matter; Figma keeps the values live. Listing every bound variable is noise: every padding and radius (chosen 2026-10-26) | Listing every bound variable |
