# Doc card v5: the documentation pilot layout

Status: spec
Reviewed: 2026-10-15 — needs revision
Date: 2026-10-15

## Goal

ThroughLine's Figma doc card today is a component set with a hand-made header and
one scripted band (Usage, `scripts/lib/doc-card-render.figma.js`, renderer `'4'`).
Manyfest's "Documentation Pilot" artboard (file `0AgaYH2xuGNKKDW1pRYLkg`, page
"🗄️ Documentation template", artboard `23546:2623`) shows a better shape: a dark
header, then stacked white bands for specimen, variants, properties, usage,
accessibility and tokens, with live instances and token swatches in them.

After this ships, every documented component gets a card in that shape, rendered
from its record plus what Figma already knows (its properties, variants and
variables). The card works for any design system and uses no particular brand.
The chrome (header, band titles, chips) comes from two kit components the
designer can restyle.

## Non-goals

- Anatomy, Content, Platform differences, Related, and live Do/Don't examples.
  Each becomes its own issue (decision 22).
- A separate docs page. Cards stay where they are (decision 6).
- A separate light/dark kit preview (decision 13).
- Figma slots. No band uses one (decision 14).
- Copying Manyfest's brand, fonts, colours or `_Doc/Band` slot structure.
- Changing the record schema. The record stays prose and the structural facts are
  read from Figma (decision 3).

## Decisions

| # | Decision | Chose | Why | Rules out |
|---|---|---|---|---|
| 1 | Who draws the chrome | Hybrid. Kit components in Figma for the header, band titles, ledes and chips; the renderer draws each band's content (tables, example rows) in tested code | Designers restyle the chrome in Figma; content layout stays testable | Everything drawn in code; everything a hand-made template |
| 2 | Which bands ship | The "ready now" set: Header, Specimen (the live set, untouched), Variants & meanings and States (both with live instances), Properties (from Figma), Usage (text lists plus Do/Don't as text), Accessibility, Tokens used (swatches). Later, each as its own step, cheapest record additions first: live Do/Don't examples and Related, then Content, then Platform differences, then Anatomy last | Ships what the record and Figma already support; holds back anything that needs new record fields | Doing the whole pilot in one release; Anatomy before the rest |
| 3 | Where structural facts come from | Properties, variant axes and token values are read live from Figma at render time. The record stays canonical for prose | Figma already has them, and copying them into the record would add a second source that can drift | Adding properties or token values to the record |
| 4 | Brand | None. Bind to the project's own semantic variables and text styles, recorded like `docCardVariables`. A missing name stops the run and names it; nothing has a hard-coded fallback. The header uses an inverse surface if the project has one, otherwise the plain surface | Must work on any design system | Manyfest's look; hard-coded hex or font fallbacks |
| 5 | How the kit is found | Created on first need on a `Documentation Kit` page, tagged with shared plugin data, recorded as `figma.docKit` in `design-system.json`, and found by its tag after that | Survives renames and moves | Finding the kit by node name |
| 6 | Where cards live | They stay where they are, wrapped around the live component set, and become the full artboard | The set doesn't move, so instances stay attached | A separate docs page; moving sets |
| 7 | How a card is addressed | The card frame gets shared plugin data `throughline` / `docCard` = the component name. `doc-card-payload.mjs` takes a component name, not a node id. An untagged card is found the way it is today, then tagged on its first render | Node ids aren't stored anywhere today and go stale | Passing node ids around |
| 8 | What the variant and state examples are | Instances of the default variant with one axis changed. A missing combination is noted in its row and in the run summary | Shows each option on its own, without a full matrix | Dropping the whole matrix in; silently skipping a missing combination |
| 9 | How tokens are shown | Colour tokens get a swatch bound to the variable. Other tokens show their name and resolved value. A name that doesn't resolve is listed as missing | The swatch stays live when the variable changes | Static hex swatches; leaving missing tokens out without a word |
| 10 | What the Properties band shows | Every `componentPropertyDefinitions` entry, including variant axes with their options, with its type and default | It's the full contract a designer works against | Only the variant axes |
| 11 | How provenance shows | A band whose content is all `ai-inferred` / `best-practice` (none `imported` / `user`) gets a chip labelled **"Unreviewed"** | The user rejected "Draft" ("doesn't quite feel right"); "Unreviewed" says what's actually missing | A "Draft" label; a provenance chip in the header (see 15) |
| 12 | Empty bands | Not rendered. Specimen always is | No empty sections | Placeholder bands |
| 13 | Light and dark | One kit that follows the variable mode | Modes already handle it | A second kit; a preview of both modes |
| 14 | How the template is built | Only `_Doc/Header` (the whole header) and `_Doc/Band header` (title, lede, Unreviewed chip) are kit components. Each band is a frame the renderer makes, holding a `_Doc/Band header` instance and the content. Its surface, radius and padding are bound to recorded variables. Specimen is the same frame with the live set inside | A main component can't sit inside an instance, so the Specimen band can't use a slot. One band shape for every band, and no first-ever slot to build | Manyfest's `_Doc/Band` with a slot; giving Specimen a different band shape |
| 15 | Who owns the status chip | One chip in the header: the existing status (`Stable`, `Final`…), now a text property on `_Doc/Header`, still written only by finalize. The renderer writes title, summary and date. The Unreviewed chip is on bands only | One owner per field; no repeated chip | A Draft chip in the header; the renderer writing the status |
| 16 | Width | 1440 or the specimen's width plus padding, whichever is bigger. Every band fills the width. The column grid goes, and each band lays out its own table or two columns | Wide sets (Button has 108 variants) have to fit | The 480-wide column grid; a fixed 1440 |
| 17 | Band order | Header (summary) · Specimen · Usage (description as its lede, then when to use / use something else, then Do and Don't in two columns with a green or red rule) · Variants & meanings · States · Properties · Accessibility · Tokens used | Usage is the text people read first; the reference tables go lower | The pilot's order, with Usage lower down |
| 18 | What the hash proves | Two hashes. `recordHash` covers the part of the layout that comes from the record: Node predicts it and a mismatch fails the run, as today. `render` covers the whole layout, including what was read from Figma: it's stamped for `docs:check` with nothing to predict it against. The summary returns the rows read from Figma so they can be checked by eye | Node can't see the Figma reads, but it can still prove the record arrived intact | Dropping the prediction; pretending Node can predict the whole render |
| 19 | Migration | Renderer v5. Existing cards report `layout-upgrade-available` and upgrade on their next render: the old header frame becomes a `_Doc/Header` instance, the existing set is wrapped in a Specimen band without leaving the card, the old `Usage` band is deleted, and the new bands are added | Instances stay attached; same upgrade path as v4 | Rebuilding cards from scratch; a one-off migration script |
| 20 | New variables and text styles | `figma.docCardVariables` gains `surfaceBand`, `surfaceHeader`, `textOnHeader`, `radiusBand`, `toneCaution`. A new `figma.docCardTextStyles` has `title`, `bandTitle`, `body`, `caption`. Both are picked once, written back, and read on every render. Projects that already have the nine fill in only the new ones. `Body/Default` stops being hard-coded and becomes the suggested `body`. Manifest schema 7 → 8 adds `docKit` and `docCardTextStyles`, both defaulting to null. A missing name stops the run | Same pattern as the nine roles; nothing guesses between renders | Hard-coded style names; a separate config file |
| 21 | Once the kit exists | Designers own it. The renderer never redraws an existing kit component; it only sets that component's properties by name. A deleted or renamed property stops the run and names it | A designer's restyle must survive the next render | The renderer quietly rebuilding or "repairing" the kit |
| 22 | Release steps | Step 1: schema 8, kit, header, Specimen band, tagging and lookup by name, v4 migration, Usage band. Step 2: Variants & meanings and States with live instances, plus Properties. Step 3: Accessibility and Tokens used. Each step is a v5.x with its own live run on the sample. The later bands (decision 2) each get a GitHub issue once this spec lands | After Step 1 the card already looks like the pilot; later steps add bands without changing the frame | One big release |
| 23 | Testing | The planner stays pure. The values the renderer reads from Figma (properties, available variants, token values) are passed in as plain data, so Node tests cover every band, including missing combinations, missing tokens and skipped empty bands. Live proof for each step: all 14 sample cards re-rendered on `OCiZiGpsJ4ncPD8r205BjC` with the record hash matching Node's; one run on a second file; and a fresh agent running `/document-component` from the command file alone | The renderer only runs in Figma, so the logic has to live where Node can test it | Renderer logic that can't be tested; live proof on the sample only |
| 24 | Other callers | component-builder Step 4.5, the storybook-chromatic-builder finalize step and component-pipeline stage 3 change no logic: they pass the component name instead of a node id and pick up v5 automatically. Audit item 11 also checks the card's tag, that the kit is recorded, and that no band uses a raw value | Every caller goes through `doc-card-payload.mjs` already | Each caller rendering its own card |
